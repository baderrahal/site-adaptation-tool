## 3. The eight buttons

Since Bader's changes of 28 Oct 2026 (docs/design/13-workflow-changes.md, approved on the canvas) the add-in has nine numbered buttons in this order: 1 Set up site, 2 Read data, 3 Review data, 4 Check, 5 Floors and ramps, 6 Levels, 7 Place villas, 8 Walls, 9 Report, and two named ones, Site Adaptation Rules and Update from report. Every button number of section 3 is the new one. The map from the numbers of the mock of 25 Oct: Check was 3 and is 4, Place villas was 4 and is 7, Walls was 7 and is 8, Report was 8 and is 9, and Set up site, Read data, Floors and ramps and Levels keep 1, 2, 5 and 6. 3 Review data, Site Adaptation Rules and Update from report are new. The title of this section keeps the words the test of R343 reads.

### What every button shares

- One transaction per button. The model changes of a real run happen in one Revit transaction named by the button, such as "Site Adaptation 7 Place villas". A failure preprocessor keeps warnings as issues (WarningCollector of R86) and an error, an exception, a read back that does not match or a commit that does not end committed rolls the whole transaction back. A TaskDialog then shows the reason and the step line of the pane stays as it was. Two steps run outside that transaction because the Revit API does not allow them inside one, each before it: the load of an unloaded link type and the reload of one whose file changed, of button 7 Place villas, on a confirm of its own, and the shared parameter file setting of button 1, put back after the transaction ends. Buttons 2 Read data, 3 Review data, 4 Check and 9 Report change no model element, nor do Site Adaptation Rules and Update from report until its Apply (5f). A file a button writes from what the model holds, `site.json` of button 1 and the level Excel of button 6, is written inside the transaction after the read back, to its temporary name (Work files below), and a failure to write it rolls the transaction back. After the commit it is moved onto its name. A move that fails, such as File.Replace onto a level Excel the user holds open in Excel, leaves the step not Done (Steps below) and the temporary file in place, and the TaskDialog and the run log name the file and say another program holds it open, so the user closes it and runs the button again. The report Excel of button 9 Report is written the same way, to its temporary name before the record of its run and moved after it (R382, planned).
- Nothing changes until the user confirms, as the round prompt asks of every button. With "Dry run first, change nothing" ticked, the default, a button first runs its dry run: no transaction, no link loaded (R86), nothing written but its own log and its outputs under `dry\<run id>\` of the work folder, which no later button reads, then its summary, the counts and the list per plot, with Cancel and Apply. Apply checks the hashes of the inputs again and runs the real run on the same inputs. Unticked, the button writes no dry folder and shows no list per plot, but it still shows the summary, the counts it will place, move, skip and leave, and asks Apply or Cancel before any write. Button 1 has the buttons Dry run and Apply in its own dialog, and its Apply is the confirm (R382, planned).
- Scope. The pane chooses Whole project (every unit plot of the plot table inside the border), Neighbourhood (the unit plots of one NBH by the area key of R256, never an IM letter) or Plot list. A plot list is official numbers typed in the TextBox, parted by commas, spaces or line breaks: each a whole number, leading zeros dropped as R81 drops them, or a range of two such numbers joined by a hyphen with the lower first, such as 2290-2299, which holds every number between them the plot table holds, a number given twice counted once. Button 1 always works on the whole project, its check points included. The scope applies from button 2 on: button 2 reads every file whole and then holds the scope against the plot table it wrote, buttons 3 to 9 take only the plots of the scope. A token that is no number and no range, a range written high to low, a number or a range the plot table holds no plot of (R113), an empty plot list and a neighbourhood with no unit plot each stop the button before any change with a message naming it, such as "Plot list: 2299-2290 is a range written high to low" or "Neighbourhood 013 holds no unit plot in the plot table" (R366 planned).
- Element tags. Every element a button places carries an Extensible Storage entity of the schema SiteAdaptation_Placed. A schema name and a field name hold letters, digits and underscore only, so SiteAdaptation.Placed with its dot would make SchemaBuilder throw. The fields: plot (the official number), kind (link, generic, yard, ramp, boundaryWall), part (the edge of a wall, else empty), run (the run id), profile, placedId (the UniqueId of the element when the tool placed it) and placed (the values the tool gave it, rounded by R385: for a link its internal origin, rotation and mirror flag, for a floor its outline and top, for a wall its line, base and top). A second run collects the elements of every version of the schema with an ExtensibleStorageFilter and keys them by plot, kind and part (R368 in Common/Tags since 4h-1, R383 planned).
- A second run, item by item of the plan in the scope, reports and leaves by default:
  - Tagged and equal to the plan: skipped and counted as already placed.
  - Tagged, equal to its own placed values but not to the plan: the plan changed, so the element is moved or updated in place and listed with the change.
  - Tagged and off its own placed values: changed by hand after the run that placed it. It is listed with what differs and left. The summary offers Leave, the default, or Set to the plan for each such element, and only the elements the user sets are changed. The tool never reverts a hand change on its own.
  - Tagged and gone, deleted by hand: placed again only when its plot is in the scope, and listed as placed again. Outside the scope it is only listed.
  - Two elements with one key, when Copy, Mirror or a paste carried the entity to a new element: an issue of the plot. The element whose own UniqueId equals the placedId of its entity is the one the tool placed and stays the tool's, the other is listed as a copy of plot n and never changed, moved or deleted. When no element or more than one holds its own UniqueId, every element of the key is listed and left and the item is skipped.
  - An element of the same plot and kind with no entity, placed by hand or by a past job: never changed, the item is skipped with the reason already placed, not by this tool, and listed, as R87 and R114 skip a plot whose number the parameter holds.
- Schema versions. Each version of a schema has its own fixed GUID and its own name, SiteAdaptation_Placed and then SiteAdaptation_Placed_2, and Common lists every GUID ever used with its field names. A run looks each listed version up by Schema.Lookup and reads an old entity by its field names. When it changes such an element it writes the entity of the latest version and deletes the old one in the same transaction, so an element an earlier add-in tagged is still found and never placed twice (R368 in Common/Tags since 4h-1, R383 planned).
- Stops. A button whose earlier step is not done, or whose input file is not chosen or not on disk, says which one and stops before any change: for example "5 Floors and ramps needs step 4" or "2 Read data needs Curbs, the file is not on disk". It never guesses an input (R382 planned).
- Steps. Each button has a line in the pane: Done, Done with [n] issues, Ready or Needs step [n] (R366 planned). A step is Done when its last real run committed with no issue, on the scope it has now and on the inputs it read then, held by one SHA-256 over every input of the step: the files of the pane it reads, Settings (config/project.json) and every config file beside it that the worker or the build reads for that step (cad_layers.json, floor_outlines.json, prototype_offsets.json, road_surfaces.json, area_codes.json, plot_numbers.json, second_source.json, the answer of the worker lists the files it opened), the rules file, the override list and the project position file. Every output its run record lists must also be on disk under its name with the SHA-256 the record gives, so a move that failed after the commit leaves the step not Done. A file is hashed by its content. A folder input, Road surface and Prototypes, is hashed by the list of the files the step uses in it, each with its name, size and last write time, not by their content: the 13 prototype files are 1,027 MiB and the 18 LandXML files of the snapshot 226 MiB, the content of the 13 hashed in 1.16 s with the files in the cache against 0.014 s for the list (RAN, round_addin\logs\hash_times_pr49.txt), and the pane works out the step state at every document switch and settings change, over a gigabyte each time from a cold cache or a network drive. A copy over a file keeps the write time of its source, so a button that reads a folder file also hashes its content as it reads it, the run log keeps that hash (R1), and a content hash that differs from the last run's marks the step and every step after it to run again at that run. Done with [n] issues when the last real run left n issues, Ready when the steps it needs are done, and Needs step [n] names the first step it needs that is not. The steps each button needs (Bader, 28 Oct 2026, docs/design/13-workflow-changes.md, Order: each step needs the one before, and 9 Report needs 4 Check): 2 needs 1, 3 needs 2, 4 needs 3, 5 needs 4, 6 needs 5, 7 needs 6, 8 needs 7, 9 needs 4. 9 needs 4 only, not 8 (CHOSEN by Code in Lane B 5a, kept by Bader's answer to Q144), so the pane shows 9 Ready once 4 is done. Button 1 needs only the settings. 13-workflow-changes.md gives Site Adaptation Rules and Update from report no step they need, so 5c and 5f set it when they build them. An input changed since a step makes that step and every step after it need running again.
- Work files. Every file the worker or the add-in writes, the reads, plans, checks, run logs, the override list of Save overrides, the two Excel files and the answer of the worker, is first written to `<name>.tmp-<run id>` in the folder of its name and closed, then moved onto its name, by File.Replace when the name is there and File.Move when it is not, the answer last. A move that fails leaves its temporary file and an issue naming the file. A name holding .tmp- is never read, and a run deletes those of earlier run ids it finds. So a partial file of a run that failed, timed out or was killed is never taken as an output, and a read is reused only when the answer of its run lists it with the SHA-256 the file on disk has (R347 planned).
- The log. Each run writes `run_<button>_<time>.json` to the work folder: the rules applied by id (CLAUDE.md, a line per rule applied), the inputs and their hashes, counts, issues, the library line (the version and file of Common and Newtonsoft.Json loaded) and free memory before and after (R383 planned).
