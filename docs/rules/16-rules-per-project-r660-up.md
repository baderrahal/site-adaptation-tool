## Round R2 C3 rules of build-2, the rules per project, no Revit call

Bader's order of the round: each project holds its own rule set beside its project profile, never in code. A shipped template is read only. A rule value has a source, computed, rule, person entered, default or missing, past only in past job mode, and a missing value is never guessed.

- **R660 Rules from a template.** Input: a request of the command rulesSetup with the roles template, projectFolder and config, and Who. The template is rules/templates/manual.json by choice of the person, the texts M01 to M15 of one named manual Rev 06 as Bader approved them, copied so no run reads the rules profile, past-job.json holds the past job measures and is never a default. Output: project_rules.json in the project folder with formatVersion, fromTemplate, beforeBuild warn and every template rule with status not confirmed, a rule with no value or a blank kept null with source missing and a mark, then the fixed rules of R663, and one line in rules_log.jsonl beside it. The run is refused with nothing written for no person, a project that already holds rules, a template with no rule, a repeated id or an id the tool keeps, a value whose source is not rule, default or past, no value with a source other than missing, a project folder inside the git work tree, an input root of config or a rules/templates folder. A template with a value tagged past is refused unless the request itself names projectRules.pastJobMode, the mode of config alone is not enough, and this goes by what the template holds and not its file name. Test: dotnet/SiteAdaptation.Tests/ProjectRules/RulesCommandTests.cs and RulesTemplateTests.cs, tests/acceptance/test_r2_build.py.
- **R661 One rule changed.** Input: a request of the command rulesChange with the roles rules and config, Who, RuleId and NewValue. Output: a new value sets source person entered, status confirmed, confirmedBy and confirmedWhen and takes off the mark. The value the rule already holds confirms it and keeps its source, whole and decimal forms of a number being the same value, since the request has no third field. A null, blank text, empty list or object, a number JSON cannot write such as NaN or Infinity, or a list or object holding one, is refused with its reason and nothing written, a value is never cleared. Two whole numbers compare exactly, 2 and 2.0 are one value, a list or object compares by its values. The runner does not mark this input as the command changes it, so the command itself refuses a file under rules/templates, any file not named project_rules.json and a file in the git work tree or an input root of config, each with nothing changed. A rules file or template that is no whole JSON gives a plain line. Each log line holds a run id. A write that fails adds a second line with the same run and rule and the field failed, whatever failed, and a reader pairs the two: the failed line cancels the nearest earlier line of that run and rule, as run ids can repeat. A kill between the first line and the write leaves the first line alone, and R662 then says the file and the log differ. Test: RulesCommandTests.cs, R640_WorkerSeamTests.cs, tests/acceptance/test_r2_build.py.
- **R662 Before Build setting.** Input: beforeBuild and the rows of project_rules.json, and rules_log.jsonl beside it, read by RulesForBuild.Check. Output: a row counts as confirmed only with status confirmed, a person, a last log line of that rule holding its value and naming that person. A row whose value differs from its last line, or a confirmed row with no line, counts as not confirmed and an issue names it as changed outside the tool or a run that stopped. A not confirmed row with no line is taken as rulesSetup wrote it, a hand edit of one cannot be seen and it stays not confirmed. beforeBuild must be the last logged setting, warn when none is logged, a file that says otherwise gives BlockingLine. With no log every row counts as not confirmed and an issue says so, and the setting of the file stands. A line a stop cut short is passed over. Then warn, the default and what an absent setting reads as, gives an issue naming how many of how many rules are not confirmed and the build goes on. Block gives BlockingLine. Any other word gives BlockingLine and never reads as warn. A rule with no value is never confirmed. rulesChange with the rule id beforeBuild changes the setting to warn or block alone, logged as any change. Test: RulesForBuildTests.cs, RulesCommandTests.cs, tests/acceptance/test_r2_build.py.
- **R663 Fixed rules and the log.** Input: the fixed rules fixed.saudiChecks, fixed.noGuessedValue and fixed.everyChangeLogged, which the tool holds and no template does, and every setup or change. Output: rulesChange refuses a fixed rule by its id, whatever the file says of it. RulesForBuild.Check says when the file changed or lost one and goes by its own. fixed.saudiChecks holds no value, source missing, and says the checks are not defined yet and none ran, see Q514, in the file and in an issue line at every Build. Each change adds a line with who, when in UTC, rule, old and new to rules_log.jsonl beside the rules, before the rules file changes, so a stop between the two leaves a line to look into and never an unlogged change. A write that fails adds a second line with failed and its reason. The log is held with no other writer for the whole change, a second run is refused. A request with no person changes nothing. Test: RulesCommandTests.cs, RulesForBuildTests.cs, tests/acceptance/test_r2_build.py.
- **R664 Rules for a build.** Input: RulesForBuild.Check with the path of project_rules.json or null, the config with projectRules.ruleIds, manualName and pastJobMode, and the mode of the request, where null takes no past row whatever the config says. Output: RulesChoiceLine, BlockingLine, Issues and Rules, each rule with Id, Name, Value, Source, Rule, Status and Marked. A config with neither list gives BlockingLine in plain words and no rules, a saved project's older copy reaches this. A null path gives the line that asks once, the choice of R660, naming the manual, and every rule of ruleIds missing and marked, never a past measure. A rules file not on disk or not usable gives BlockingLine in plain words and every rule missing. The file is not trusted on its word: no value, source missing, an unknown source or a past value outside past job mode each give a missing and marked rule, status confirmed with no person is not confirmed, and a rule the file lost is missing and takes nothing from a template. Test: RulesForBuildTests.cs, and through the build the tests R2-C2-build-1 holds in tests/acceptance/test_r2_build.py.
